# Матрица требований

Тестовое задаёт конкретный сдаваемый модуль из трёх функций; бизнес-требования
описывают будущий MVP. Области реализации разделены явно, без заявления о
несуществующих интеграциях или приёмке заказчиком.

| Требование тестового | Реализация / проверка |
| --- | --- |
| Python 3.11+, hints, docstrings, стиль | `pyproject.toml`, все Python-модули, Ruff |
| Исходные dataset.json и catalog.json | Значения скопированы из приложений, хеши в отчёте |
| normalize_movement, восемь полей, None | `normalize.py`, эталон всех полей M1–M8 |
| Даты, единицы, упаковки, signed correction | Параметризованные тесты валидных/невалидных случаев |
| SKU в разных форматах / по названию | SKU-шаблон, однозначные алиасы, объяснение в RESULTS |
| Все поля forecast_demand | `forecast.py`, шесть контрольных расчётов |
| Детерминированность и отсутствие LLM в арифметике | Чистые функции, Decimal, дата из данных |
| Пропуски и удвоение расхода | Последнее календарное окно, диагностика, тесты |
| Упаковка и минимальная партия | Decimal-ceiling и независимые пограничные примеры |
| Confidence, короткая история, волатильность | Прозрачная формула и порог в config.py |
| answer_question, семь интентов, сущности | `questions.py`, 15 исходных + 5 дополнительных вопросов |
| Неоднозначность / отсутствие параметров | unknown + уточнение, отдельный статус отсутствия данных |
| Числа из расчётного модуля | Рендер результата forecast.py, без генерации чисел |
| Рекомендованная LLM, обязательный fallback | Опциональный локальный Ollama и полностью автономные правила |
| pytest, зависимости, запуск в 1–2 команды | requirements.txt, main.py, --verify |
| README и RESULTS | Инструкции, все таблицы, методология, фактические замеры |
| Мотивация, роль, срок участия | MOTIVATION.md — личная часть требует ответа кандидата |
| Публичный репозиторий и ссылка в резюме | Подготовлено локально; публикация и изменение резюме не выполнялись |

| Бизнес-требование | Статус в данном тестовом |
| --- | --- |
| Однопользовательский интерфейс, чат | Локальный web-прототип, правила без ключей |
| Синтетический набор, единая модель | Данные приложения, контракт в DATA_MODEL.md |
| Остаток, среднее, потребность, страховой запас, точка заказа, объём, стоимость | Реализовано для трёх SKU с историей |
| План / бюджет месяц, квартал, полгода, год | 30/90/180/365 дней, раскрыто допущение постоянного уровня |
| Дефицит, низкий запас, излишек, отсутствие расхода, резкий рост | Расчётные признаки и диагностика; отсутствие расхода не равно отсутствию всех движений |
| Дата заказа и объяснение каждого расчёта | Предварительная дата, формулы, период, источники, допущения |
| Изменение горизонта/лимита, сценарий загрузки | Параметры, интерфейс, разбор явного процента |
| Экспорт / история расчёта | JSON и Markdown, хеши исходных файлов |
| Не менее 20 вопросов и сценариев | 15 исходных + 5 дополнений, pytest |
| Время ответа до 15 секунд | Фактические локальные показатели в RESULTS; LLM отдельно не измерялась |
| FEFO, срок годности, партийные списания | Нет исходных партийных остатков/сроков: объяснение нехватки данных |
| Ценовая динамика по поставщику | Нет истории цен/поставщиков: запрашиваются данные |
| Себестоимость и маржа SPA-услуг | Нет норм, процедур и цены услуги: дальнейшее развитие |
| Помесячная / категорийная разбивка, сверка с прошлым бюджетом | В исходном наборе нет категории и прошлых планов; не имитируется |
| Филиалы | Поддержан внешний context.location_history; приложение содержит лишь общий снимок |
| Интеграция ABS, БД, Docker, production-роли | Не обязательны для трёх функций; не заявлены как готовые интеграции |
| KPI 95% расчётов, 90% рисков, 15/20 содержательных ответов | Есть контрольные проверки; нет независимого бизнес-набора для подтверждения этих KPI |
| Демонстрация и подтверждение заказчиком | Локальная демонстрация подготовлена; подтверждение заказчика не получено |
| Автозаказы, оплата, автосписание | Не выполняются, согласно исключениям бизнес-документа |

При дальнейшем расширении приоритеты: датированные заказы и качество снимков;
затем партии/сроки и rolling-план; после этого история цен, услуги и прогноз
загрузки. Модель спроса сравнивается на достаточно длинной истории и отложенных
периодах прежде, чем усложнять её или обещать точность.
